# AI.md

How I used AI to build this submission: the tools, the prompts that worked, what the AI got wrong and how each mistake was caught, and how every result was verified.

## Summary

- **Tools.** Claude Code in VS Code, running Claude Opus 5.5:
  - plan mode for the design;
  - two research subagents that checked current library APIs before any code was written;
  - forked subagents that built the frontend, the browser tests and the docs in parallel;
  - three fresh-context reviewer agents for an adversarial review at the end, and a subagent that fixed the web app's findings while the main session fixed the rest.
- **My part.** I wrote the brief, set the quality bar and the constraints, and chose the design direction and the GitHub setup. I approved the plan and its phase prompts before any code existed, and steered at each decision point. The AI wrote the code, the tests and the docs.
- **The rule that mattered most:** nothing counts as done until it is verified. Each fix comes with a test that failed before it; the claims in the docs are checked against the code; the images are scanned.
- **Result:** 333 automated tests:
  - 50 contract tests;
  - 100 API unit tests;
  - 68 API end-to-end tests;
  - 93 web tests;
  - 22 browser tests.

  Beyond the tests, a call-by-call recorded run against the production Docker image (repeated on the final image, with the same results), both images at 0 HIGH/CRITICAL vulnerabilities, and green CI.

- **The review.** Three reviewers with no prior context reported 43 findings. 35 were fixed, and the rest were documented, accepted or kept, each with its reason. A fourth then read the whole change before it was committed and found 8 more, all fixed. See [Review triage](#review-triage).
- **What was corrected.** The [correction log](#correction-log) has 34 entries: mistakes and gaps in the AI's work, and places where its memory of a library was out of date. Each says how it was caught:
  - tests, live runs and linters;
  - reading the libraries' current source instead of trusting the model's memory;
  - fresh-context review.

## Workflow

1. **Plan mode, before any code.**
   - The AI read the spec and checked the machine: Node 22.17, a stopped Docker daemon, and the wrong `gh` account signed in.
   - It looked up the current major versions on the npm registry instead of trusting its training data. Nest 12, Mongoose 9, React Router 8, Vite 8, Zod 4, Vitest 5, MSW 3 and TypeScript 7 were all newer than the model's knowledge.
   - Two research subagents spent about 18 minutes each reading current docs and package sources. Several of the decisions below came from what they found.
2. **A phase playbook.** Each phase had a written prompt with its own "done" criteria (below). I approved them with the plan.
3. **Backend first.** It was written in the main session, because the auth core needs one consistent author. Then came a live run against the production Docker image, recorded call by call.
4. **Parallel phases.** Forked subagents inherit the whole conversation. They built the frontend, the Playwright suite and the docs while the main session worked on Docker, CI and security scans. Each fork was told what it owned and was not allowed to commit. The main session reviewed every fork's work before committing it.
5. **Verification at every step.** Each fix got a test that failed on the old code. The live runs used real HTTP and MongoDB, Trivy scanned both images, and CI ran on every push.
6. **Adversarial review.** Three reviewer agents with no prior context each read the task PDF and audited one area against its scoring rubric. Their findings were triaged, fixed and verified again. A subagent fixed the web app's findings; the main session reviewed its work, found one bug in it, and fixed everything else itself.
7. **A final review before committing.** One more agent with no prior context read the whole uncommitted change, fixes included, looking for anything the fixes broke or missed. Its findings were fixed the same way, and the recorded run was repeated on the final image.

## The prompts

The AI drafted these in plan mode from my brief. I reviewed and approved them before the first line of code, and each phase was executed against its prompt.

**P1 Scaffold.** "Scaffold an npm-workspaces monorepo: apps/api with the latest Nest CLI (npm, strict TypeScript), apps/web with create-vite react-ts, and e2e/ for Playwright. Keep the TypeScript version each generator pins unless the whole toolchain supports a newer one. Add Prettier, .editorconfig, .gitattributes (LF), .nvmrc, husky + lint-staged, and docker-compose with MongoDB. Done when lint, build and test pass on the empty apps."

**P2 Backend.** "Build the auth API in apps/api to this contract: [endpoint table]. Controllers handle HTTP only. Services hold the rules and depend on abstract repositories. Only repositories touch Mongoose, and they return plain objects. Services throw domain errors, and one global filter turns every error into RFC 9457 problem+json with a stable `code`. Security: argon2id; constant-time sign-in for unknown emails; a 15-minute JWT in the body; an opaque rotating refresh token in an httpOnly SameSite=Strict cookie scoped to /api/v1/auth, stored hashed, where reuse revokes the session. Guards are global and routes are protected unless marked @Public(). Rate-limit the auth routes; add helmet, a strict ValidationPipe and Mongo filter sanitising; validate env at startup and fail fast. Add pino request logging with request IDs and redaction, Swagger at /api/docs and a Mongo health check. Unit-test every service branch."

**P3 Backend E2E.** "Write e2e tests that boot the real AppModule through the same bootstrap function as main.ts, against mongodb-memory-server. Cover every requirement and every error path. Then run the stack with docker compose, call every endpoint over HTTP, record each request and response, check the documents in MongoDB, and write docs/E2E_TEST_REPORT.md: verdict first, requirement coverage, scenario tables (Step | Call | Expected | Got), database checks, test counts, and the full request/response log."

**P4 Frontend.** "Build apps/web: sign-up, sign-in and a protected page showing 'Welcome to the application.' with sign-out. Design brief: [editorial paper and ink]; do not use gradients, glassmorphism, emoji, centred blurred cards, default Tailwind/shadcn styling or Inter. Engineering: data routes with loader guards; RHF + Zod with the API's exact password rules and a live checklist; the access token in memory only; refresh on load and on 401 (single-flight per tab, Web Locks across tabs); server errors mapped to fields by `code`; CSS Modules with tokens; self-hosted fonts; WCAG AA; keyboard-first; reduced motion. Unit-test the schemas, forms and HTTP client with Vitest, Testing Library and MSW."

**P5 Browser E2E.** "Write Playwright tests against the compose stack: sign-up → welcome → reload keeps the session → sign-out → protected route redirects → sign-in; validation and server errors; an axe scan on every page. Then check the app at desktop and mobile widths, fix visual or console issues, and capture README screenshots. Add the results to the E2E report."

**P6 CI/CD and docs.** "Add GitHub Actions: lint, typecheck, unit + e2e tests and build for api and web; a Playwright job on docker compose; publish images to GHCR on main only when every check passes. Write README, ARCHITECTURE (with sequence diagrams), CLAUDE.md, and AI.md from the real session log."

**P7 Review.** "You are screening 50 submissions of this exact task against this rubric: [scoring criteria]. Find every reason this one would lose: bugs, security gaps, unclear code, missing tests, AI-looking UI, and doc claims the code doesn't back up. Report file:line, severity and a concrete fix."

**P8 Ship.** "Create the repository under Mostafay65, push the history, wait for CI to pass, then make it public and report the link."

Some details changed once the research came back. The prompts above are as approved; the changes and their reasons are in the correction log. Examples: Vitest instead of Jest, Nest 12's built-in security headers instead of helmet, and route middleware instead of loader guards.

### What made the prompts work

- **"Check the current docs and source before relying on memory."** This caught the largest class of errors. Nest 12 generates ESM projects with Vitest, not CommonJS with Jest. TypeScript 7 has no compiler API, so the toolchain can't use it yet. React Router 8 runs loaders in parallel, so they can't guard each other. Zod 4 can trip a strict CSP.
- **"Done when…" criteria in every prompt.** Each phase ended with commands that had to pass, not with "looks good".
- **"Every fix needs a test that failed before it."** Early on, the old code was swapped back in for two fixes to watch the new test fail, and the CSP test was marked as a known failure until its fix landed. In the review round, this was done for every fix a test can show.
- **Narrow ownership for subagents.** "You own these files; if you find a bug elsewhere, report it with evidence instead of fixing it." The browser-test agent reported two real app bugs this way, and the main session fixed them with proper tests.
- **"Verify every claim in the docs against the code."** Checking the architecture guide this way turned up a real race in refresh-token rotation (see the correction log).
- **Reviewers with no shared context.** They don't inherit the builder's assumptions, and the rubric gives them a concrete standard to judge against.

## Correction log

Each entry gives what was wrong, how it was caught, and what changed. The review's 43 findings are in [Review triage](#review-triage); the entries below are the other corrections, including those made while fixing the findings.

### Caught by reading current sources, not memory

- **The Nest 12 project template.** The plan expected Jest and CommonJS. The Nest 12 CLI generates ESM with Vitest and oxlint. The plan and the tooling were updated.
- **TypeScript 7.** It is a native compiler with no programmatic API, so the Nest CLI, typescript-eslint and the Swagger plugin can't use it. The project stays on TypeScript 6.0.3, as both generators pin it. Later, when Dependabot proposed TypeScript 7, the latest typescript-eslint still declared support only below 6.1, so the major is ignored, with that reason written in the config.
- **Nest 12 built-ins.** Security headers, the cross-site request check, cookies and Standard Schema validation are all built in now. This replaced helmet, cookie-parser and class-validator. It also let one shared Zod package validate the API, generate the OpenAPI document and drive the web forms.
- **Nest's cookie `maxAge` is in seconds**, not milliseconds as in Express. The source was read before the cookie code was written.
- **CORS and the cross-site check.** Reading Nest's `CrossOriginProtection` source showed that allowed CORS origins must also be trusted by the cross-site check, or every POST from them gets a 403. Origins also had to be bare, without a trailing slash. Both are now enforced at startup.
- **React Router 8.** Loaders run in parallel, so a parent loader can't protect its children. Route guards became route middleware.
- **Zod 4 and the CSP.** The browser suite saw a CSP violation on every page load. Zod's source showed it probes `new Function` when a schema is built, and skips the probe in jitless mode; its source comment names strict CSPs as the reason. The web app now turns jitless mode on before any schema loads.

### Caught by tests and live runs

- **Invalid JSON.** It returned the raw parser message and no request ID, because Express parsed the body before the request ID existed. The request ID middleware now runs first, the JSON parser is registered after it, and the error filter answers with a fixed message.
- **The refresh cookie's `Max-Age`** was 604,799 instead of 604,800, because rounding down lost a second to elapsed milliseconds.
- **Swagger** showed no example bodies, and listed the password's minimum length as 1, because the real rule is a refinement. Examples and descriptions were added to the shared schemas.
- **Unlogged requests.** Requests rejected before routing (invalid JSON, oversized bodies, cross-site writes) never reached the request logger. The error filter now logs them.
- **A timing leak.** The live run's timing table showed the first sign-in with an unknown email after a restart taking 65 ms, against 35 ms for a wrong password, because the throwaway hash was created lazily. It is now prepared at startup. In the final recorded run, over 20 samples each, the medians are 33.9 ms and 34.6 ms.
- **Identical access tokens.** Two sign-ins within the same second produced byte-identical tokens. Each token now has a random `jti`.
- **No `Cache-Control`.** API responses had none, so browsers kept `/users/me` after sign-out (found by the browser suite). Every response now says `no-store`, and API responses carry no ETag.
- **Zod 4's error format.** The first version of the new configuration tests expected the field name before the message. Zod 4's `prettifyError` prints the message first, then `→ at JWT_ACCESS_SECRET`; the tests failed, and their patterns were corrected.
- **A test that relied on the gap.** Once tokens without `exp` were refused, an existing end-to-end test failed: its hand-made token had no `exp`. It got one, and a separate test now checks that a token without one is refused.
- **A slow test, and a fix that broke 39 others.** One cross-tab test failed once at 1,023 ms, just over Testing Library's one-second wait. Raising the wait meant importing Testing Library in the test setup, which registered its unmount step before the setup's own. Vitest runs those steps in reverse order and skips the rest when one fails, so apps from earlier tests stayed mounted and 39 tests failed. The setup now unmounts first, explicitly. The suite then passed four runs in a row, and three runs at once.

### Caught in review and while checking docs

- **A design flaw, before any code.** The first refresh-token design keyed sessions by a guessable ID, so a forged secret could revoke someone else's session. It was redesigned as one record per token, looked up by its SHA-256 hash and grouped into families; a forged token matches nothing.
- **A race in refresh rotation.** It was found while checking the architecture guide's claim that reuse locks out "both the thief and the user". The old token was claimed before its successor was stored, so a racing request could revoke the session before the winner's new token existed, and that token survived. Now the successor is stored first.
  - A unit test that forces that ordering fails on the old code.
  - An end-to-end test runs the race against MongoDB.
- **Cookies cleared too eagerly.** A failed refresh cleared the cookie on any error, so a database outage would have signed everyone out. Now it clears only when the token itself is rejected.
- **Untrusted error statuses.** The error filter trusted any error that carried a numeric `status`, which could have surfaced a library's internal message to clients. That branch was removed.
- **Docs written from memory.** The first draft of the architecture guide had a log example written from memory and a rate-limit description that was wrong. Both were replaced with the real log line and the actual per-route limits.
- **`AbortSignal.any` and the build target.** The subagent fixing the web findings joined the new request time limit and the caller's signal with `AbortSignal.any`. Vite 8 builds for Safari 16.4, Chrome 111 and Firefox 114, and `AbortSignal.any` arrived later (Safari 17.4, Chrome 116, Firefox 124), so in those browsers every such request would have failed as a network error. The main session caught it while reviewing the agent's work. A small helper replaced it, and a test that removes `AbortSignal.any` fails on the agent's version.
- **A test name that claimed too much.** "Every link and button is at least 44px square" measured only the masthead links and the form buttons; the link inside a sentence is smaller, as WCAG allows. Caught while writing the test report; the test was renamed to say what it measures.

### Caught by scanners and the dependency bot

- **TypeScript in the production API image.** It is an optional peer of the Swagger package and flagged `devOptional` in the lockfile, so `--omit=dev` kept it and `--omit=peer` had no effect. The fix is `--omit=optional`, which took `node_modules` from 117 MB to 90 MB.
- **Base images.** Trivy found 6 HIGH issues in `node:24-alpine`, all inside the bundled npm, and 56 HIGH/CRITICAL in the full nginx image, mostly from modules a static server never uses.
  - The API image drops the package managers.
  - The web image moved to nginx's slim variant.
  - Both now have 0 HIGH/CRITICAL, and the web image went from 83 MB to 35 MB.
- **An end-of-life nginx branch.** Dependabot proposed nginx 1.31. Checking the tags showed that the 1.29 branch we had pinned no longer gets fixes (stable is 1.30, mainline 1.31). The image moved to the stable branch.
- **A gap in the update policy.** Once the MongoDB image was covered, Dependabot proposed MongoDB 9.0, and its checks passed. The config held back new Node majors but had no such rule for MongoDB, while the docs, the recorded run and the test database all name 8.2. MongoDB majors are now ignored, with the reason in the config, and the pull request was left for Dependabot to close.

### Caught by linters, Git and the agents' own checks

- **oxlint:** `no-misused-spread` on a string spread, unbound method references, and a numeric sort without a comparator.
- **Lightning CSS** doesn't follow a chain of CSS Modules `composes` across files, so buttons rendered in the wrong typeface.
- **React Router 8** warns for a loader-only route without `element: null`. The warning went unnoticed at first because Vitest's agent reporter hides console output from passing tests. The web tests now fail on any console warning.
- **Two copies of Vitest.** Run from a shell whose working directory had a lower-case drive letter (`d:\`), 33 web tests failed with "Invalid Chai property: toBeInTheDocument". The subagent traced it to `@testing-library/jest-dom/vitest`, which imports Vitest itself and, through the differently spelled path, loaded a second copy that received the matchers. The setup now adds jest-dom's matchers to the `expect` the tests use. CI, on Linux, was never affected.
- **A measurement taken too early.** The subagent's first touch-target measurement ran before the web fonts had loaded, so it measured the fallback font. It measured again after `document.fonts.ready`.
- **Line endings.** Multi-line edits made with Python on Windows wrote CRLF line endings. Git warned about `.env.example` (`.gitattributes` asks for LF); Prettier had already rewritten the code files. The file was converted, and a scan of every changed file for CRLF came back clean.

## Review triage

Three reviewer agents, each starting with no context, audited one area against the task's rubric with prompt P7: the API, the web app, and security with operations and docs. They reported 43 findings (11, 14 and 18). Several overlapped, so the tables below have 38 rows.

- **Fixed:** 35. Most were fixed as suggested, three in a different way (the reason is given), and one only in part.
- **Documented instead of changed:** 1. Access tokens outlive sign-out by up to 15 minutes, because revoking them would cost a database lookup on every request.
- **Accepted:** 1. Ten moderate `npm audit` findings, all in lint tooling that never ships.
- **Kept, by my decision:** 1. The visual direction.
- **Parts of fixes declined:** 8, each with its reason.

Where a test can show the problem, the fix comes with one that fails on the old code. That was checked by putting the old code back: 16 new API tests and both new nginx tests failed on it, and the subagent did the same for each web fix. The nginx change that re-resolves the API's address was checked by hand, by moving the API container to a new address.

### Final review

Before anything was committed, one more agent with no prior context read the whole change, the review fixes included, looking for what they broke or missed. It reported 8 findings, and all 8 were fixed. Six could be shown by a test, and each of those tests was run against the old code and failed.

| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A refresh had the same 10-second limit as every other request.
